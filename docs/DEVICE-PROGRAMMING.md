# Device output repair: research, implementation, and limits

Research checked on 8 October 2026. This feature changes a programmable pedal's stored keyboard/mouse outputs; it is separate from input calibration and Treadory's logical action mappings. The app remains a static frontend. The website installs no native service or system remapper. A separately installed Treadory extension maps readable USB inputs across permitted browser tabs; it does not change hardware outputs.

## Direct programming contract

The initial adapter accepts only these identities: `0c45:7403`, `0c45:7404`, `413d:2107`, `1a86:e026`, `3553:b001`. These are protocol candidates, not hardware-certified product models. At least one is reused by non-pedal equipment, so VID/PID alone is insufficient.

All gates are required:

1. Explicit selection through **Check connected pedal**, not automatic restoration or configuration import.
2. Product name identifies a FootSwitch/Foot Pedal.
3. Exactly one matching vendor-defined collection has output report 1 and output report 8 with 56 payload bits each, and input report 8 with 56 payload bits. The browser reports actual item sizes/counts; missing metadata fails closed. Protected keyboard/mouse collections do not qualify.
4. Only numbered framing is supported: the report ID is passed separately and its 7-byte payload excludes that ID. No speculative writes to alternate report IDs.
5. Each of three stored slots is queried twice, serially. Replies must be identical and have a supported 8-byte reconstructed record. Types 0, 1, 2, 3 and 0x81 can be preserved. Strings, macros, malformed lengths, unsupported bits or silence revoke the session and require a new check/manufacturer tool.
6. New outputs are limited to ordinary Space/Enter/Escape/function keys, mouse left/middle/right buttons, or no output. Logical app actions such as Play/Pause are not device-output promises; the target application decides what a stored key does.

The check sends only read-query commands. EEPROM programming starts only after explicit review and **Save to pedal**. No program request is serialized into app configuration, auto-replayed after refresh, or triggered by a model selection, demo event or import.

Before a write, all slots are queried again and compared to the reviewed settings. The complete desired snapshot is copied and validated before asynchronous work. The start/header/data sequence includes every slot, including byte-exact unedited modifiers, mouse movement and alternate trigger configuration. Writes are serialized with 30 ms spacing and a one-second delay after start. Every slot is read twice after the save; success means exact byte equality with the requested snapshot.

Normal raw input is detached before the programmer opens its selected interface. App actions are released during checks/saves; Connect Pedal is unavailable until the programming handle closes. Cancellation, permission denial, changing model, timeout, unmount and unplug clean up the separate session. Changing model cannot silently redirect a pending write.

Original settings can be downloaded as a device-output backup (different from app configuration JSON). After a successful change, **Restore original outputs** requires its own review and explicit write to the same checked session. Backups remain downloadable after an unsuccessful write. A partial or mismatched save closes/revokes the session and reports uncertainty; it never automatically retries or applies an unverified rollback. Use the backup's original outputs with the manufacturer tool if recovery is required.

## Validation and remaining hardware work

- `npm test`: 25 tests, including identity/descriptor gates, packet framing, supported settings, correct middle/right mouse bits, stable reads, complex unedited outputs, explicit restoration, stale settings, query timeout, partial-save detection, cancellation and parallel-operation rejection.
- `tests/repair-browser.mjs`: 15 WebKit scenarios with a virtual EEPROM pedal. Includes Middle Right Click → Space, disabled-output verification without an impossible calibration step, backup download, full save/readback, stale legacy DOM calibration invalidation, device-specific verification guidance, restoration, unsupported identities/interfaces/macros, multi-device ambiguity, unplug, failed verification, cancellation, a superseded input chooser, manufacturer routes, no-WebHID fallback and expanded responsive layout.
- 7 main UI scenarios, 5 tools UI scenarios and 14 audit regressions remain in the test set. Production build/SEO checks verify the static frontend and responsive layout.

**No actual pedal has been programmed or certified by this work.** The virtual device intentionally emulates the chosen protocol; it cannot independently prove that a real device uses it. The UI states that physical hardware verification is pending. A firmware variant that fails the descriptor/read checks is a manufacturer-tool fallback, not a reason to loosen the guards.

Before calling any physical firmware version hardware-verified, record its exact identity/descriptor/firmware, original outputs, and observed press/release events; change just one output; confirm other slots and modifiers; verify the changed OS event in a separate application; reconnect/power-cycle and repeat; explicitly restore originals and verify them. A readback alone does not establish persistence across a power cycle, switch health, or target-app behavior. If the real report descriptor differs from the numbered contract, collect its documented transport/USB trace before implementing another adapter.

## Current monitoring flow

Generic DOM input testing was removed because the browser cannot identify the physical source of keyboard/mouse events. Decoded USB presses own history rows; nearby DOM mouse events are optional annotations, never proof of device output. Firmware programming remains gated by the same exact protocol checks. VEC wording explicitly separates unavailable direct programming in Treadory from potentially fixable desktop mappings. X-keys links directly to its official browser programmer, which supports stored hardware macros.

Local virtual test fixtures referenced in this audit are excluded from the public repository. Current extension installation and validation status is documented in [EXTENSION.md](EXTENSION.md).
